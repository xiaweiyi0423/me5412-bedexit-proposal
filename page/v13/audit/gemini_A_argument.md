从坐→站（Sit-to-Stand, STS）生物力学和简化建模的角度来看，第 13 版用线性规划（LP）加入座板托力来补齐“起步有多难”的论证，思路非常清晰。但仔细读 `seat_support.py` 和 `controller_v13.py` 的代码及结果，核心模型里有两处硬伤，直接动摇了“起步不是瓶颈”和“推力上限可设 0.4–0.6”这两个核心结论。

### 1. 髋关节力矩平衡方程写错了：漏掉了骨盆下方的座板托力（严重度：高）

* **在哪里**：`model/calc_v13/seat_support.py` 的 `lp_rows` 函数（第 34–38 行），以及网页 `#why` 节的“模型的简化与局限”说明。
* **代码与原文证据**：
  ```python
  Mh = moment_about(Hp, P, upper)
  Mk_t = moment_about(K, P, upper + thighs)
  # seat force (vertical, at x_s) on the pelvis: muscle moment term = -(x_s - J_x) * Fs
  hip = (np.array([Mh.a[0], Mh.a[1], -(x_s - Hp[0])]), Mh.b, 2 * sub.hip_ext, 2 * sub.hip_flex)
  ```
  其中 `x_s = Hp[0] - 0.04`（座板合力点在髋关节后方 4 cm）。所以 `-(x_s - Hp[0]) = +0.04`。LP 里的约束是：`Mh.a · F + 0.04 * Fs + Mh.b <= 2 * sub.hip_ext * t`。
* **为什么是问题**：
  1. **隔离体（Free-Body Diagram）画错了（确定的事实）**：`moment_about(Hp, P, upper)` 切开的是髋关节，取的是**髋关节以上的头、躯干和双臂（`upper`）**作为隔离体。座板托力 $F_s$ 作用在臀部/坐骨结节（即骨盆/大腿近端，属于髋关节以下的部分），**根本不作用在髋关节以上的 `upper` 隔离体上**。只要躯干倾角和手部受力不变，无论座板在屁股底下托多少力，髋关节伸肌为了维持躯干不往前栽倒所需的力矩（$\approx 72\text{ N}\cdot\text{m}$）是完全一样的。代码把 $F_s$ 加进髋关节方程，在力学上不成立。
  2. **就算把骨盆算进隔离体，正负号也反了（确定的事实）**：如果假设髋关节以下切开、且 $F_s$ 作用在髋后方 4 cm（$x_s < \text{Hp}_x$），向上的托力 $F_s$ 会对髋关节产生一个**顺时针（使躯干前倾/屈曲）**的力矩，需要**更大的**髋伸肌力矩去抵抗。但代码里 `+0.04 * Fs` 跟重力矩 `Mh.b`（在躯干前倾时为负值，如 $-72\text{ N}\cdot\text{m}$）相加，反而**抵消**了重力矩。
  3. **后果**：这个项虽然力臂只有 4 cm（在 $F_s = 0.5\text{ BW} \approx 294\text{ N}$ 时偷减了约 $11.8\text{ N}\cdot\text{m}$，相当于把髋关节负担少算了约 0.074 的 effort），但它在物理上是错的；而且网页“模型的简化与局限”里专门拿“作用在髋后方 4 cm，改成 2 cm 或 7 cm 几乎不变”来当卖点，懂力学的老师一眼就能看出隔离体不对。
* **怎么改**：
  把 `seat_support.py` 第 37 行的 `hip` 里的 `-(x_s - Hp[0])` 改成 `0.0`（座板托力只卸载膝关节和踝关节，不卸载髋关节），重新跑 `seat_support.py` 和 `controller_v13.py`，更新 JSON 和网页上的数字。

### 2. 模型在起步阶段发生了“姿态作弊”：为了省膝盖的力，让人在刚起身时把上身挺直（严重度：高）

* **在哪里**：`model/calc_v13/seat_support.py` 的 `solve` 函数，以及计算结果 `seat_support_start_effort_heel08`。
* **代码与数据证据**：
  在 JSON 结果中，当 `P1 cap25` 在 $h = 0.42\text{ m}$、推力上限 `0.3`、`0.4`、`0.5`、`0.6` 时，算出来的起步 effort 分别是 `0.230`、`0.213`、`0.155`、`0.103`。
  为什么当座板托力上限是 `0.3` 时，从 $0.42\text{ m}$ 到 $0.50\text{ m}$ 的 effort 卡在常数 `0.230`、`0.229`？为什么托力上限 `0.5` 时 effort 能低到 `0.155`？
* **为什么是问题**：
  1. **数学机制（确定的事实）**：在没有座板托力（离座，$F_s=0$）时，全身质心必须移到双脚上方（COP 约束），所以躯干必须大幅前倾（比如 40°–60°），此时髋关节重力矩很大，膝关节力矩也很大。但当允许座板托力 $F_s > 0$ 时，系统的总支撑面（BOS）从“双脚”扩大到了“座板（$x_s$）到脚尖（$t_0$）”的巨大区间！LP 优化器立刻发现了这个漏洞：**只要座板还受力，人就不需要把重心移到脚上**。于是优化器为了减小髋关节力矩，直接选择了**躯干接近直立（`trunk = 0°` 或很小角度）**，同时靠双手使劲往上拉横杆、双脚只维持最低的 $0.3\text{ BW}$。
  2. **生物力学与设计矛盾（确定的事实 + 合理推论）**：
     * 网页第 4 步（`step_04`）明确写着：“握紧‘起’开关，**身体前倾**、脚往下踩，把座板上的力降到半个体重以下。”
     * 但 `0.155` 这个数字是在**身体不前倾（甚至后仰/直立）**的姿态下算出来的！如果人真的按生物力学常识先做躯干前倾（哪怕前倾 35°–45° 准备离座），髋关节的重力矩就已经达到约 $60\text{–}80\text{ N}\cdot\text{m}$，光髋关节的 effort 就已经高达 **0.25–0.35**，根本不可能是 `0.155`！
     * 反过来，如果老人真的按优化器算出来的“上身直立、纯粹靠手拉横杆和腿蹬”把座板卸到 $0.5\text{ BW}$ 以下让座板升起来，那么当座板升到 $0.63\text{ m}$ 要离座（$F_s \to 0$）的那一刻，他必须突然在高处把躯干往前甩 50° 才能把重心移到脚上——这在准静态和防跌倒上都是危险的。
* **怎么改**：
  * **方案 A（改模型，最诚实）**：在 `seat_support.py` 求起步 effort 时，规定姿态（`shank`, `trunk`）不能随便选直立，或者要求**人体加手力的等效压力中心（地面反力 COP，不含座板）必须已经接近脚跟**（即人已经摆好前倾准备起身的姿态），再看需要多少膝伸力矩来把座板卸载到 `cap`。但要注意：一旦这样算，髋关节在起步前倾时的 effort 就会接近离座时的 effort（约 0.23），“起步只用 0.16”的结论会变成“起步和离座所需的最大发力差不多（瓶颈在髋关节保持前倾），但省掉了低位最致命的膝关节峰值力矩”。这个物理解释其实**更符合生物力学常识**（低位坐→站真正的敌人是膝关节力矩，座板托力精准卸载了膝关节，而髋关节的屈曲前倾本来就是人坐着也能做的）。
  * **方案 B（改口径，不动大框架）**：如果时间来不及大改模型，必须在网页 `#why` 的“模型的简化与局限”里诚实写明：“起步 effort (0.16) 是在准静态最优姿态（躯干尚不必大幅前倾，因座板仍分担支撑面）下求得的下界；若老人在起步时已提前大幅前倾躯干，髋关节负担会接近离座水平，此时座板托力的主要作用是削峰膝关节力矩。”

### 3. 推力上限 `cap = 0.4` 对目标人群其实不可用，“0.4–0.6”的范围定宽了（严重度：中）

* **在哪里**：网页 `#why` 节左下角卡片（“起步不是瓶颈，但推力上限不能设得太低”）、表格 `#capT`，以及 `#control` 参数表。
* **原文与数据证据**：
  * 网页定义的目标人群是：最大能力 effort 在 **0.23–0.29**（P1 假设）或 **0.25–0.30**（P2 假设）。
  * 表格 `#capT` 给出在 $0.42\text{ m}$ 起步所需的 effort：当推力上限设为 `0.4` 时，P1 需要 **0.213**，P2 需要 **0.233**。
  * 控制器速度公式是 `v = k * (F_cap - F_seat)`。
* **为什么是问题**：
  1. **起步速度为 0 的死锁（确定的事实）**：`start_effort` 算的是把座板力**刚好降到等于 `F_cap`** 所需的 effort。此时 $F_{\text{seat}} = F_{\text{cap}}$，代入控制器公式得到的抬升速度 $v = k(F_{\text{cap}} - F_{\text{seat}}) = \mathbf{0}$！要想让座板以合理的速度升起来（比如留出 $0.05\text{–}0.10\text{ BW}$ 的裕量），用户实际要能把座板卸到 $0.30\text{–}0.35\text{ BW}$。
  2. **看 JSON 数据**：在 `min_seat_load_by_height_and_effort` 中，在 $h = 0.42\text{ m}$ 时：
     * 对于能力为 `0.23` 的目标用户（P1 最弱目标用户），他在 $0.42\text{ m}$ 能达到的最小座板力是 **`0.367` BW**。如果推力上限设为 `0.4`，余量只有 $0.033\text{ BW}$，起步速度只有最大速度的 $0.033 / 0.35 \approx 9.4\%$（不到 $0.3\text{ cm/s}$，几乎不动）。
     * 对于 P2 假设下能力为 `0.25` 的最弱目标用户，他在 $0.42\text{ m}$ 能达到的最小座板力是 **`0.372` BW**（而在 `0.23` 时是 `0.404` BW，根本启动不了 `0.4` 的上限）。
     * 如果再修正上面第 1 题的髋关节力矩 bug，`0.4` 上限的起步 effort 还会进一步上升，直接超过 `0.23`。
* **怎么改**：
  哪怕不改代码，也建议把可调范围从 `0.4–0.6` 改成 **`0.45–0.60`（默认 0.50）**，或者在表格旁明确加一句：“对能力接近下限（0.23）的较弱用户，推力上限不宜低于 0.5，否则在 0.42 m 处剩余卸力裕量太小、起步极慢；0.4 仅适用于能力较强、希望多锻炼腿部力量的用户。”这样老师问起来会觉得你们考虑得非常细。

### 4. `min_seat_load` 曲线在 effort = 0.23 到 0.24 之间存在近乎断崖的跳变，插值会产生伪影（严重度：中）

* **在哪里**：JSON 数据 `min_seat_load_by_height_and_effort`（`P1 cap25`，`0.42` m），以及 `controller_v13.py` 的 `min_seat(h, c)` 函数。
* **数据证据**：
  在 $h = 0.42\text{ m}$（P1）时：
  * `effort = 0.22` $\to$ 最小座板力 `0.388` BW
  * `effort = 0.23` $\to$ 最小座板力 `0.367` BW（变化 0.021）
  * `effort = 0.24` $\to$ 最小座板力 **`0.215` BW**（effort 只增加 0.01，座板力暴跌 **0.152 BW**！）
  * 同样在 `P2 arm x0.5` 的 $0.42\text{ m}$ 处，`effort = 0.29` 时是 `0.309` BW，到 `0.31` 时暴跌到 `0.145` BW。
* **为什么是问题**：
  这是离散姿态网格（`SHANKS` 步长 5°，`TRUNKS` 步长 5°）加线性规划边界导致的典型跳变：当 effort 跨过某个阈值（如 0.233 左右，正好允许某个躯干倾角的髋关节力矩通过）时，一个新的前倾姿态突然变得可行，使得座板载荷瞬间掉下一大截。
  虽然不影响定性结论，但如果老师细看仿真图（比如为什么 `weakest (0.23)` 在一开始座板力高达 0.37 BW 升得很慢，升到 0.46 m 时座板力突然掉到 0.22 BW 加速），这就是网格粗导致的台阶伪影（在 `#sims` 的“最弱的目标用户 (0.23)”蓝线上能清晰看到 6 秒附近有一个突然往下掉的台阶）。
* **怎么改**：
  把 `seat_support.py` 第 22 行的姿态网格加密，例如 `SHANKS = list(range(-10, 31, 2))`、`TRUNKS = tuple(range(0, 81, 2))`（计算时间会增加约 6 倍，但用 `Pool` 多进程也就是几十秒的事），台阶就会平滑掉。

### 5. “目标人群：抬高床站不起来，起身台能站起来”在对照组设置上有一点口径不对称（严重度：低）

* **在哪里**：网页 `#problem` 的“目标人群”框、`#why` 节右侧读数栏，以及 `#structure` 的“脚下空间”。
* **原文证据**：
  网页定义目标人群为 effort 落在 `0.23–0.29` 之间的人，其中 `0.29`（精确值 `0.291`）来自 `compare_v11` 中“抬高床 0.58 m + 扶手（脚跟在髋前 10 cm）”，而 `0.23`（精确值 `0.233`）来自“起身台 0.66 m + 横杆（脚跟在髋前 8 cm）”。
* **为什么是问题**：
  在 README 和 `#structure` 里你们很诚实地交待了：如果两边都用相同的脚下空间（10 cm），起身台在 $0.66\text{ m}$ 的离座 effort 是 **`0.244`**（比 `0.291` 低 16%），而不是 `0.233`（低 20%）。
  但在网页 `#problem` 和 `#why` 的主叙事里，全部直接用了 `0.23`（即 8 cm 的结果）来画目标人群边界和跑仿真（如仿真 2“最弱的目标用户 0.23”）。如果审稿人/老师质疑“为什么给自己的方案多留 2 cm 的脚跟优势来框定目标人群”，你们在 `#structure` 虽然有尺寸解释，但在 `#why` 节没有提这个 `0.233 vs 0.244` 的前提。
* **怎么改**：
  在 `#why` 节提到“0.23–0.29”时，顺手括注一句“（若脚跟空间与床同取 10 cm，则为 0.24–0.29）”，跟 README 的严谨口径保持完全一致，滴水不漏。

### 总体判断与最值得先做的一件事

* **总体判断**：这份第 13 版方案在逻辑闭环、控制安全边界和工程诚实度上已经远超一般的研究生课程项目，把准静态生物力学模型直接接到状态机仿真里驱动用户行为的做法非常亮眼。但**扩展模型（`seat_support.py`）对座板托力的力学处理过于粗糙**，出现了“托力跨过髋关节卸载上身”的物理错误和“靠直立躯干刷低起步 effort”的优化漏洞。
* **最值得先做的一件事**：**立刻检查并修正 `seat_support.py` 第 37 行的髋关节力矩系数（把 `-(x_s - Hp[0])` 改为 `0.0`），并查看最优解的 `trunk` 角度**；如果改完后在固定前倾姿态下髋关节 effort 接近 0.23，请把网页话术从“起步整体只需要 0.16 effort”微调为“座板托力把低位最致命的**膝关节**负担降到了 0.16 以下，使起步不再比高处离座更难”。这样既保住了设计结论，又在生物力学上完全站得住脚。
